Code review — test-gcp-dataflow-dataform-cloud-composer (full-project, HEAD 2d0151e)

No open PR; this is a full-codebase review. Findings ranked by severity, most important first. The two most serious candidates from the prior review (committed billing-account IDs, cross-project Dataform resolution) both verified as resolved/false-positive.

1. "Extend, not rewrite" is proven narrower than the headline. [Medium — high confidence]
The extensibility proof (make verify-project2 → local/scripts/verify_project2.sh) runs tests/project_smoke.py, which exercises only the shared in-memory engine (harness.generate, RecordRouter, run_batches, TransformEngine, doors) — not the Beam Dataflow entry points. Those entry points hardcode project1 names: pipelines/json_producer/pipeline.py:39-40 (ENRICHED_TABLE="account_enriched", TARGET_TABLE="account_target"), :45 (SchemaField("account_id",…,mode="REQUIRED")), :90 (doc["accountId"]); pipelines/data_enrichment/pipeline.py:31-32,36; pipelines/file_processor/pipeline.py:54 (SRC_TABLE="account_src"). A real project2 (DEPOSIT) Dataflow run would fail — data_enrichment requires account_id (deposits lack it), json_producer KeyErrors on doc["accountId"] (project2 has depositId). The proof is real but proves "no engine file modified + shared engine runs project2 in-memory," not "project2 runs end-to-end through the same Dataflow lane." The GCP evidence run exercised only project1 (ACCOUNT, 76 rows); project2 has never run on Dataflow or GCP.

2. Python pipelines interpolate run_id into SQL via f-strings. [Low-Medium — high confidence, bounded blast radius]
All three Beam pipelines build DELETE/SELECT with f-string run_id: pipelines/json_producer/pipeline.py:118-121,124-127,166-173; pipelines/data_enrichment/pipeline.py:113-116,118-121; pipelines/file_processor/pipeline.py:341-343,405-407. run_id is externally supplied (composer/dags/mig_000001_1.py:119, templated from trigger config). This is a real injection anti-pattern, but the input is operator-supplied (not external untrusted input), and the DAG was not triggered in the GCP run (ran via the local orchestrator). The same codebase already demonstrates the safe pattern — composer/dags/mig_000001_1.py:237-244 uses @run_id + bigquery.ScalarQueryParameter, and the Java side is parameterized. Fix: route the Python pipelines through pipelines/common/storage.py BigQuery.query extended with parameter support, matching the DAG's pattern. (The prior review rated this L1/Low; I raise it to Low-Med only because of the inconsistency with the rest of the codebase.)

3. No project2 Dataform models exist. [Medium — honestly documented]
dataform/definitions/ contains only account_src.sqlx and account_curated.sqlx. contracts/mappings/mapping-project2.yaml:34 references curated.table: deposit_enriched, but no SQLX model builds it. So "extend, not rewrite" also fails on the Dataform side: a new project requires a new .sqlx file. local/scripts/verify_project2.sh:10-14 honestly admits this ("a new project adds one new .sqlx (not config-driven)"). This is a claim-vs-reality gap, not a hidden defect — but the headline claim oversells what's config-driven.

4. Terraform project_id default bakes in a real GCP project id. [Low-Medium]
terraform/envs/dev/main.tf:77-80 defaults project_id to mig-000001-1-dev; :32 hardcodes the tfstate backend bucket mig-000001-1-dev-tfstate (README:395 acknowledges). terraform init/apply without TF_VAR_project_id (README:246) targets a real project. billing_account correctly has no default (:87-90). Milder than the resolved H1 because this is the migration project's own id, documented in README, and overridable — but a default pointing at real infrastructure is a footgun.

Known & documented simplifications (checked, acknowledged, not blocking):
- M3 — insertAll (streaming API) for target writes, not FILE_LOADS (batch). pipelines/file_processor/pipeline.py:293-304 docstring states this is "wrong at target volume" and the FILE_LOADS swap is "not yet done." Exercised on real GCP at 76 rows. Production-scale gate.
- M4 — whole source table read into the Beam driver (not ReadFromBigQuery). The DAG's beam_pipeline docstring (composer/dags/mig_000001_1.py:131-135) explains this is why Flex Templates were abandoned.
- M5 — Kafka OAUTHBEARER callback not implemented; GCP run used --sinks gcs. Kafka path unexercised.
- M11 — no partitionBy/clusterBy in SQLX models. Acceptable at prototype volume.
- M13 — Java app images default to :latest (composer/dags/mig_000001_1.py:78), overridable via MIG_JAVA_IMAGE_TAG (documented :42-44).
- Java Workload Identity auth gap — composer/dags/mig_000001_1.py:211-218 honestly documents that the Java apps (raw HTTP, no SDK) don't pick up Workload Identity automatically and need a metadata-token seam; MIG_GCS_TOKEN intentionally not set. Until wired, the L/R lanes only work against emulators.
- Config-switch consistency — pipelines/common/config.py:87-114 exposes three independent switches (TARGET_PROFILE / BQ_TARGET / MIG_RUNNER) with no cross-validation; an inconsistent combination (e.g. TARGET_PROFILE=local + BQ_TARGET=real) is undefined rather than rejected.
- run_dataform.py:65-66 textual stdout.replace("mig-local", project) is a blunt retargeting instrument — exact only because mig-local is a distinctive string unlikely to appear as data; a future run_id or record value containing that substring would be corrupted. Latent fragility, not a current bug.

Overall. This is a well-engineered, honestly-documented prototype that the 2026-08-04 GCP evidence run proves works end-to-end on real infrastructure (E → T+R → L, 76 rows, balancing gate closes). The prior review's serious findings (H1–H8) are resolved, fixed, or previously confirmed. The actionable residue is: (1) tighten the "extend, not rewrite" claim to match what verify-project2 actually proves, or extend the proof to the Dataflow lane; (2) replace the f-string run_id SQL with the parameterized pattern the rest of the codebase already uses; (3) decide whether project2 needs Dataform models (and say so explicitly). Nothing here blocks the September MVP at prototype scale; items M3/M4/M5/M11/M13 and the Java WI gap are the real production-readiness gates.
